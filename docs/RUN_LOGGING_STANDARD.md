# Rust-Tools 运行日志规范

本规范区分**已经接入**与**仍待验证或补齐**。本次日志代码已请求构建，但尚未运行自动测试或通过 Windows/Linux 人工验收；构建结果出来前不得宣称通过。

## 架构与接入状态

业务层报告事实，`pytools-core::run_logging` 提供任务编号、事件、逐输入账本及结果结构；界面负责中文输出和日志路径，底层 Excel 引擎不直接向终端打印。现有 `engine_diag` 和 `SummaryRunEvent` 暂时保留。用户视图、结构化事件和运行汇总分别服务于操作、定位和统计；结构化事件不代替现有运行 JSON。

当前统一事件与运行汇总已接入：1-1 时序宽表汇总及目标写入、1-2 按使用区域汇总、1-3 命名区域与批注汇总、1-4 表头路径比对、1-5 配置预校验；2-1/2-2 去重与 2-3 追加；3-1/3-2 静态打印与 3-3 预校验；4 类菜单中的转换、归档、批量重命名、Sheet 重命名、文件前缀、提交完整性检查；专用报表 7-1 至 7-8 的主要执行入口；7-1/7-2 配置管理。旧 JSON 字段与业务耗时继续保留，新增统一运行编号、JSONL 事件或运行摘要。

接入粒度依入口现有报告而异：部分配置驱动任务报告的是配置项统计，不是文件统计；部分专用报表从既有报告事后适配文件结果，异常中断时不能保证逐文件最终状态。此类入口用 `input_stats_available=false` 标明缺项；统计不完整时不能把 0 当作事实。转换和归档的 `selected_path_count` 是用户选择的位置数量（可能包含文件夹），文件账本按展开后的文件或计划行计数。快捷打开操作只保留简短结果消息。自动化覆盖已补充部分模块与 CLI 菜单，但全量测试和真实样本验收仍待用户授权执行。

## 终端输出和级别

使用本机时间 `[YYYY-MM-DD HH:mm:ss] [INFO|WARN|ERROR|DEBUG] 内容`。`INFO` 表示关键阶段、进度和摘要；`WARN` 表示需注意或跳过；`ERROR` 表示失败；`DEBUG` 表示细节。`OK`、`SKIP` 如有使用表示业务结果，不是严重程度。默认用户模式应显示进度、结果和可执行的中文说明，避免逐单元格和逐行刷屏；无需颜色，重定向时不得依赖 ANSI。开发者模式可展示现有结构化诊断，命令行机器接口的 JSON 必须保持兼容。

已接入的交互入口默认输出简洁中文状态行，不向普通用户倾倒整份 JSON；命令行机器接口继续输出 JSON。配置表的「全局配置」可设置 `日志模式` 为 `普通`、`详细` 或 `关闭`，启动时读取；已有命令行参数优先。主阶段行使用统一本地时间戳与级别。原始错误可能含敏感值；普通模式只记录用户可理解的原因和定位，底层错误链仅在开发者模式写入 `details`。对于无法安全分类的错误使用通用建议。

## 时间与编号

持久化事件 `timestamp`、汇总 `started_at`、`ended_at` 使用含偏移的 RFC 3339；耗时来自 `Instant` 单调时钟。`run_id` 用功能编号、进程、时间和进程序列生成；迁移时通过 `RunTracker::with_id` 复用既有编号。一次执行的全部事件和汇总必须关联同一 `run_id`，禁止将输出文件编号误当作任务编号。

## JSONL 与运行汇总

`LogEvent` 含 `schema_version`、`timestamp`、`level`、`event_name`、`run_id`、`feature_id`、`stage`、`status`、`message`，可选 `file_index`、`file_name`、`file_path`、`sheet_name`、`cell_address`、`engine`、`elapsed_ms`、`error_code`。不适用字段省略。UTF-8 JSONL 每行一条事件；`EventWriter` 使用 create-new 避免覆盖，逐事件写入，异常时尽可能保留已有行。

`RunSummary` 有开始和结束时间、总耗时、整体状态、逐输入结果和统计，并可包含 Sheet、记录、输出、性能和错误摘要及诊断文件路径。用户视图的诊断路径写成相对日志目录的 `run-events/<文件名>`；开发者视图可以记录完整路径。现有运行 JSON 应以新增字段扩展，不能删除旧字段。`output_paths` 只记录已报告的输出；业务数据和密码不进入日志。

## 输入、Sheet、记录和输出统计

输入以用户选定的每个位置为单位，重复路径也分别计数：`selected = succeeded + failed + skipped + cancelled + pending`。`attempted` 表示进入实际处理的输入数量，可包含最终失败、跳过或取消；`pending` 含尚未开始或尚未完成的输入。非法的重复状态转换应拒绝；只读成功不代表业务成功。聚合任务的输入处理状态与最终汇总文件保存状态分开，保存失败时整体必须失败。

`discovered` 仅在目录扫描实际提供数量时记录。Sheet 指标记录实际发现、尝试、成功、失败、跳过的工作表；每项必须以工作簿、Sheet、阶段为上下文，适用时加单元格或区域。记录计数按实际业务解释，区分读取、处理、写入、筛选和去重；不能以行数替代文件数。输出统计只数已经保存的工作簿及可确定的 Sheet、行数和输出路径，不推测文件大小或保存结果。

1-2 的 `completed_files` 记录输入已汇总，`output_stats.saved` 独立反映汇总输出，`performance_stats` 保留读取和写入耗时。没有可汇总区域时为 `NO_OP`。已发现 Sheet 的精确最终失败阶段仍依赖业务层事件；未提供的定位不得臆造。

## 整体状态

`SUCCESS`：所有应执行的业务步骤及关键输出成功，正常筛选跳过可以存在；`PARTIAL_SUCCESS`：既有成功输入又有失败输入；`FAILED`：关键配置或共享输出失败，或输入失败且没有成功输入；`CANCELLED`：用户取消；`NO_OP`：正常执行但没有需要变更或可汇总的数据。任务中止时未开始和未完成输入仍为 pending；禁止把未执行项目算作成功。各入口应在有足够业务证据后判定，不以是否出现 WARN 代替状态。

## 错误码与定位

按实际用到的错误定义稳定码，如 `EXCEL_READ_FAILED`、`OUTPUT_WRITE_FAILED`、`INTERNAL_OPERATION_FAILED`；必要时增加 `FILE_`、`FORMAT_`、`SHEET_`、`RANGE_`、`CONFIG_`、`DATA_` 前缀。错误包含功能、阶段、可用的文件名、Sheet/坐标、可理解的原因及建议。不要把引擎报错直接断言为程序问题或文件问题。当前部分入口映射稳定码并在开发者视图保留底层诊断；旧运行记录仍可能含原始路径或错误文本，不能假设历史资料已经脱敏。

## 文件位置与保留

沿用每项业务已有的日志目录配置；1-2 和静态打印的 JSONL 位于其 `run-events` 子目录，例如 `PT-6-1_<run_id>.jsonl`。各路径不能依赖工作目录偶然正确。日志写入失败应提示但不改变业务结果。默认不清理；「全局配置」可填写 `日志保留天数` 和 `日志最大占用MB` 的正整数，在交互菜单启动时按修改时间处理 `run-events` 中可验证且已有 `run_finished` 事件的 JSONL，先清过期文件再按最旧优先削减到限制内；未完成、无法识别、其他后缀、子目录及符号链接不清理。该策略目前不处理旧运行汇总 JSON，不是文件写入时的滚动轮转；日志管理尚未实机验证。

## 隐私与性能

普通模式的结构化摘要只记录文件名；诊断路径为相对日志目录的路径。开发者模式可保留绝对路径及底层错误链。任何模式均不得记录单元格原始内容、密码、令牌或完整敏感配置；日志不上传网络。旧业务日志可能仍包含路径或原始错误，不能假定已脱敏。事件以任务、工作簿和必要的 Sheet/阶段为单位，不在单元格循环中写普通日志，不为了统计重新读取工作簿。流式写入失败应保留业务运行；热路径避免无意义的巨大序列化。

## 新增功能接入要求

每个业务入口应创建或复用 run_id，记录开始、结束、耗时和阶段；按真实业务完成情况记录文件最终状态，提供必要的 Sheet/区域定位、输出结果、用户可理解错误及关联的结构化事件。只打开目录等快捷操作可仅记录操作结果。统计缺失时显式留空，禁止推断成功；配置错误和安全风险应阻止相应操作。已有功能逐项适配时保留原业务计算、文件保护和旧 JSON 字段。
