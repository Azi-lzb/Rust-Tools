# Rust-Tools 运行日志规范

本文件是 Rust-Tools 运行日志的唯一权威规范。功能实现、事件字段和测试应以仓库当前代码为准；不得把未实现或未验证的计划写成既成事实。每次交付需单独记录本轮编译、自动测试、真实样本验收及平台验证状态。

## 2026-11-12 本轮展示契约（优先适用）

本轮日志精简要求覆盖以下旧章节中关于普通视图开始、阶段、逐文件/逐工作表成功、常规引擎回退和耗时的展示规则。用户日志只显示最终业务结果及必要异常；正常成功不逐文件、逐 Sheet 刷屏，不展示内部步骤。开发诊断持久化完整事件链，终端内容与诊断采集分离。旧 JSON 字段保持兼容；统计只以实际业务及最终验证/提交成功为依据。扫描、检查、匹配、提取和实际写入分别采集；未知不冒充零，候选修改量不冒充已提交量。业务异常不自动视为程序执行失败。

实施状态、逐菜单审计与真实捕获见根目录 RUSTTOOLS_LOGGING_SPEC.md、RUSTTOOLS_LOGGING_AUDIT.md、RUSTTOOLS_LOGGING_SAMPLES.md、RUSTTOOLS_LOGGING_ACCEPTANCE.md；文档契约不代表所有入口已完成验收。下文旧展示示例仅作兼容历史参考。

## 1. 总体架构

日志系统由公共运行日志组件和业务统计供数两层组成，并通过终端、事件流和单次运行汇总三种载体呈现：

1. **公共运行日志组件**统一负责任务开始/结束、批量进度、文件最终状态、业务异常与执行失败分类、异常定位、耗时、输出位置、详细事件写入、摘要格式及终端信息密度。它不得依赖 Excel 业务规则。
2. **业务统计供数**由业务功能提供已经实际测得的指标，例如提取/写入行数、重复组/删除/追加数、校验项/异常数、转换数、打印工作簿/工作表数、改名/冲突数及归档计划/完成数。每项功能只提供自己适用且真实采集的字段，不填充无关指标，也不自行拼接完整终端摘要。
3. **用户终端日志**仅显示最终业务结果和必要异常；已有交互与进度机制不在本轮重设计。
4. **开发者事件日志**使用 UTF-8 JSONL，每行一个可机器解析的结构化事件。
5. **单次运行汇总**扩展已有 JSON，保留旧字段并补充统一统计、业务指标和错误上下文。

事件采用与 OpenTelemetry Logs Data Model 相近的时间、级别、事件名和上下文属性组织方式；按 tracing 的操作阶段思路关联业务阶段与 `run_id`。当前实现保持本地离线写入，不接入遥测服务、远程数据库或网络监控组件。

业务层报告实际处理结果和少量适用指标；`pytools-core::run_logging` 提供 `RunTracker`、互斥输入状态、Sheet 状态账本、`LogEvent`、`EventWriter`、`RunSummary`、批量密度策略和公共摘要格式化。CLI/菜单适配层提供当前终端能力和用户可读路径，不重复拼接摘要。Excel-Core 不直接向普通用户终端打印进度。既有业务事件类型及运行历史继续保留，统一记录用于关联和补充，不代替旧运行 JSON。

`RunTracker` 保存通用状态，`BusinessIssue` 保存可选业务发现，`business_metrics` 保存各功能确实采集到的指标；`BatchLogPolicy` 和公共摘要格式化负责终端显示。CLI 只传入实际进度、结果和路径，不在业务代码里拼完整摘要。当前共享批量显示器已接入提交检查、文件转换、表头路径比对、本地文件名映射、批量重命名、文件名前缀处理、汇总类功能、配置去重、静态打印、归档、地区总分校验和工作表提取。部分历史专项报表仍沿用原有业务摘要，后续应逐项迁移；不得把未接入项描述为已完成。若某旧入口无法从其业务报告还原逐文件结果，必须把 `input_stats_available` 设为 `false`，不得把未知数填成零或推断成功。仅打开目录等快捷操作可只记录必要结果。

## 2. 终端可读日志

主要日志统一使用本地时间和格式：

```text
[YYYY-MM-DD HH:mm:ss] [INFO] 内容
```

普通模式使用简洁中文，仅显示最终结果和必要异常；交互菜单默认不倾倒 JSON。直接 CLI 命令仍可按原机器接口输出 JSON。`--log-view user|developer|off` 或全局配置“日志模式”控制视图；显式 CLI 参数优先。`OK`、`SKIP` 是业务结果标签，不是严重级别。无 ANSI 颜色的终端和重定向输出必须可读。

用户摘要只显示适用的非零业务指标和输出位置；异常才显示具体文件与简短原因，同名文件使用必要路径区分。最终文件状态只有成功、跳过、失败。运行期取消/未执行在结束时归为跳过，在处理未完成归为失败；不得转换为成功。耗时、Sheet 明细、读取/写入阶段、重算和引擎回退只进开发者诊断。

开发者的每条开始、阶段、单项结果和结束日志都应体现当前功能的实际动作、对象和结果。避免单独使用“开始处理”“处理完成”“任务结束”“工作簿处理结果”等通用文案；共用日志适配器应使用功能名，功能模块应使用准确动词和对象，例如“按工作簿内容添加文件名前缀”“按使用区域汇总工作表”“将汇总数据写入配置指定的目标工作簿”。失败日志应说明失败发生在读取、匹配、修改、保存或其他实际阶段，不得只显示“操作失败”。

## 3. JSON/JSONL 结构

统一 `LogEvent` 的必需字段：

- `schema_version`、`timestamp`、`level`、`event_name`、`run_id`、`feature_id`、`stage`、`status`、`message`

按需记录 `file_index`、`file_name`、`file_path`、`sheet_name`、`cell_address`、`config_row`、`error_code`、`engine`、`elapsed_ms`、`details`。不适用字段省略，禁止填充无意义的 `null`。`details` 仅供开发诊断，禁止放入单元格原始业务值、密码或令牌。

`EventWriter` 以 create-new 方式创建文件，逐事件追加 JSONL，避免覆盖同名运行；写入或创建失败必须提示，但不得覆盖、删除或回滚业务输出。此前已写事件尽量保留。结构化日志使用统一类型序列化，不手写 JSON 字符串。

## 4. 日志级别

- `INFO`：任务开始/结束、关键阶段、用户需要知道的进度和成功结果。
- `WARN`：可恢复问题、业务跳过、日志保存失败但业务继续。
- `ERROR`：文件、Sheet、输出或任务关键目标失败。
- `DEBUG`：高频细节、底层引擎细节及诊断上下文。

只有确实影响业务状态时才提升为 `ERROR`。跳过不自动等同失败，不能仅凭是否出现 `WARN` 判定任务状态。

## 5. 时间戳和耗时

持久化时间 `timestamp`、`started_at`、`ended_at` 使用带时区偏移的 RFC 3339。终端时间使用用户本地时间。任务耗时必须由单调 `Instant` 计算，单位为毫秒；阶段耗时也应使用单调计时。禁止以系统墙上时钟相减计算耗时。

## 6. run_id 关联

每次实际业务执行生成一个唯一 `run_id`；迁移旧入口时可用 `RunTracker::with_id` 复用原编号。该次任务的终端摘要、所有事件及运行汇总必须引用同一编号。运行编号由功能编号、进程标识、时间熵和进程序列组成；不得用输出文件编号代替运行编号。

## 7. 文件、Sheet、区域和单元格定位

输入账本以用户选择的每个位置计数，重复路径也分别计算。文件事件至少在可用时包含文件序号和文件名；开发者视图可记录完整路径。Sheet 事件关联源工作簿、Sheet 名称、阶段及操作结果；有可靠位置时记录工作表序号、单元格地址或区域。`RunTracker` 的 Sheet 账本拒绝重复发现和矛盾状态转换，并在汇总中保留文件、Sheet、阶段、坐标和错误码。不能从业务事件还原的位置不得臆造。

批量逐工作表读取、检查或修改时，用户可见的单项日志应简要标明工作簿名和工作表名，例如“工作簿「报表.xlsx」，工作表「人民币」：正在读取数据”。此类日志只显示文件名，不显示绝对路径；开发者日志需要路径时仍放在结构化字段中。读取工作簿失败、尚未获得工作表名称时，只标明工作簿名。可复用 `run_logging::workbook_sheet_context_message` 为现有进度事件补充上下文，事件适配器应传入当前工作簿和当前工作表，避免各功能重复拼接或重复打印名称。

对区域修改，按需记录 `source_sheet`、`target_sheet`、`source_range`、`target_range`。禁止为了日志逐单元格输出。

## 8. 批处理统计口径

### 输入工作簿

- `selected`：实际选中的输入位置数。
- `discovered`：目录扫描实际发现的文件数；不适用时省略。
- `attempted`：实际进入处理的文件数。
- `succeeded`、`failed`、`skipped`、`cancelled`：每个输入的互斥最终状态数量。
- `pending`：结束时未开始或尚未完成的输入数。

必须满足：`selected = succeeded + failed + skipped + cancelled + pending`。`attempted` 是处理行为计数，不能与最终状态计数相加。读取成功不代表业务成功；需要的业务步骤全部完成后才可标记文件成功。

### Sheet、记录和输出

`SheetStats` 记录 `discovered`、`attempted`、`succeeded`、`failed`、`skipped`；详细账本以文件和 Sheet 为键。`RecordStats` 当前按业务实际提供 `rows_processed`、`rows_written`。其他字段（读取、过滤、去重、匹配等）只在入口确实测量且语义明确时加入。

`OutputStats` 记录可确定的已保存工作簿数、Sheet 数和保存状态；输出路径仅包括业务层确认产生的结果。汇总输入状态与共享输出保存状态分开：所有输入已处理但汇总输出失败时，整体任务仍为 `FAILED`。PT-6-1 保留既有 `read_elapsed_ms`、`write_elapsed_ms`，并补充统一的文件、Sheet、记录、输出和总耗时统计。

## 9. 错误码与分类

错误码必须稳定且基于实际错误使用，按需采用 `FILE_*`、`FORMAT_*`、`SHEET_*`、`RANGE_*`、`CONFIG_*`、`DATA_*`、`EXCEL_*`、`OUTPUT_*`、`INTERNAL_*` 分类。当前入口沿用的具体示例包括 `EXCEL_READ_FAILED`、`OUTPUT_WRITE_FAILED`、`SHEET_OPERATION_FAILED`、`CONFIG_INVALID` 和 `INTERNAL_OPERATION_FAILED`；新增错误码前先检查现有映射。

重要错误应包含功能、阶段、可用的文件和 Sheet/坐标、易懂的原因及建议。错误链放在开发者 `details` 中；终端不倾倒长 Rust 堆栈。独立文件可恢复时继续处理后续文件；全局配置错误、共享输出失败或安全保存无法继续时终止相应任务。

## 10. 任务结果语义

- `SUCCESS`：所有应执行的业务步骤和关键输出成功；正常筛选跳过可以存在。
- `PARTIAL_SUCCESS`：至少有部分输入成功，同时存在失败或不完整结果。
- `FAILED`：关键配置/共享输出失败，或输入失败且无成功输入。
- `CANCELLED`：用户或执行控制明确取消。
- `NO_OP`：处理正常，但没有符合条件的数据或无需变更。

缺少输入、输出或 Sheet 结果时不得伪造成功。中止后未开始项目保留 `pending`；正常筛选项可以是 `skipped`。工作簿输入成功与最终汇总输出成功是两个独立事实。

## 11. 日志目录和文件命名

显式 `--log-dir` 优先；全局配置中显式填写的“日志目录”按配置文件基准目录解析。新建配置的“日志目录”留空，让程序使用默认路径；既有非空配置保持原值。未配置时，使用与当前工作目录无关的每用户可写目录：Windows 为 `%LOCALAPPDATA%\rust-tools\logs`（不可用时采用用户目录回退）；Linux 为 `$XDG_STATE_HOME/rust-tools/logs`，否则为 `$HOME/.local/state/rust-tools/logs`；系统目录不可用时回退到系统临时目录。

新结构化事件存入 `<log_dir>/run-events/<feature_id>_<run_id>.jsonl`。`UnifiedRunSession` 的统一汇总写入 `<log_dir>/run-unified/<feature_id>_<run_id>.json`。PT-6-1 等已有入口还保留旧命名/字段的运行 JSON，例如 `PT-6-1_<run_id>.json`；其他遗留业务日志也按旧接口继续保存。日志路径由配置或 CLI 参数决定，不允许默认写到 `C:\Users\AZI\Desktop\VibeCode` 根目录。

## 12. 保留和清理

默认不自动清理。全局配置可设置正整数“日志保留天数”和“日志最大占用MB”。当前清理仅在交互菜单启动时检查 `run-events` 中可验证、命名匹配且末事件为 `run_finished` 的 JSONL：先清过期文件，再按最旧优先控制总大小。未完成、无法解析、不匹配的文件，其他后缀、子目录、符号链接以及业务输出均不删除。此策略不轮转旧 JSON/文本日志，也不在每次写入时切分文件。

## 13. 隐私和安全

普通视图可显示用户需要辨认的文件名，但不默认持久化大量绝对路径；开发者视图可保留定位所需的绝对路径和底层错误链。不得记录单元格原始业务数据、密码、令牌或完整敏感配置；日志不上传网络。遗留日志可能包含历史路径或错误文本，不能假设已经脱敏。清理只能操作经过验证的诊断日志文件，禁止触碰输入、输出、配置、夹具和人工验收证据。

## 14. 性能和交互

日志粒度以任务、工作簿、Sheet 和关键阶段为主；禁止在逐单元格热循环写普通日志或为了统计重复读取大型 Excel。结构化事件逐条写入，避免反复构造大 JSON。根据真实进度更新用户反馈，不重复刷“读取中/读取完成”等无价值消息。

终端展示密度应同时考虑输入规模和终端能力。少量输入可显示适量文件级阶段；批量输入较多时，交互 TTY 使用单行动态总体进度，重定向或不支持动态刷新的终端按阶段和低频检查点输出。例行进度可合并或节流，关键阶段变化仍需显示；无论批量大小，执行失败和业务异常必须逐项记录并完整写入详细事件。跳过数量应进入最终摘要，跳过原因按规模与关注程度显示。

日志写入失败要提示并继续保留可继续的业务结果。公共组件接收各功能提供的适用指标，并负责统一格式化；禁止业务模块自行输出第二份完整任务摘要。

## 15. 菜单和业务模块接入

接入点必须位于实际 CLI/菜单业务入口或公共业务调用链，不能只在 Excel-Core 增加日志。现有主菜单范围：

1. 数据提取与汇总：提供实际读取/写入行数、工作簿/Sheet 状态和读写耗时。
2. 数据去重与追加：提供重复组、删除行和追加行；区分计划、输入处理和目标提交，失败不得被吞掉。
3. 报表打印：提供生成工作簿数和处理工作表数；区分配置预校验、生成结果及目标写入。
4. 文件处理：提供逐文件结果和实际引擎；保留原有日志历史接口。
5. 专用报表：提供实际工作簿、Sheet、配置行及保存结果。
6. 归档整理：提供计划归档数和实际归档数，记录最终状态和可恢复错误。
7. 配置与快捷操作：配置任务提供启用/成功/跳过/失败任务数和配置行阶段；仅打开资源的快捷操作可使用简短结果事件。

新增或修改入口时，优先复用 `RunTracker`、`EventWriter`、批量展示器和统一汇总；配置任务的统计必须标为配置项，不能伪装成文件计数。业务发现应计入 `business_issues`，不自动转成程序执行失败。旧运行 JSON 只做向后兼容的增量扩展。未采集的指标必须省略或声明不可用。不得改变业务算法和文件处理行为来迎合日志字段。

## 16. 示例和自动化测试

终端摘要示例：

```text
[2026-10-28 21:25:15] [INFO] 执行成功：区域汇总；选择 3，尝试 3，成功 2，失败 0，跳过 1，取消 0，未完成 0；工作表发现 4，尝试 4，成功 4，失败 0，跳过 0；处理 180 行，输出 180 行；读取 0.095 秒，写入 0.028 秒；耗时 0.142 秒；运行编号 PT-6-1-example
```

JSONL 事件示例：

```json
{"schema_version":1,"timestamp":"2026-10-28T21:25:15+08:00","level":"ERROR","event_name":"operation_failed","run_id":"pytools-pt-6-1-example","feature_id":"PT-6-1","stage":"cell_read","status":"failed","message":"工作表处理失败","file_index":3,"file_name":"机构.xlsx","sheet_name":"贷款表","cell_address":"E42","error_code":"SHEET_OPERATION_FAILED"}
```

日志测试应覆盖时间和 run_id、互斥计数和状态转换、部分失败/跳过/取消、读取成功但共享输出失败、NO_OP、同一工作簿多个 Sheet 部分失败、文件/Sheet/坐标定位、JSON/JSONL 解析、日志创建/写入失败、旧运行 JSON 字段兼容、不同菜单入口关联同一 run_id、长中文和 Windows 扩展路径，以及日志改造不改变输入和业务输出。统计/状态测试必须断言结构化结果，不得只查某个字符串。使用小型合成样本；没有授权或未运行的测试必须如实写为未验证。

## 17. 后续开发约束

新增批处理必须提供 `run_id`、开始/结束时间、单调总耗时、必要阶段、文件最终状态、适用的 Sheet/坐标定位、输出结果、用户可读错误、结构化错误和运行汇总，并有覆盖统计逻辑的测试。普通读取完成不得自动判定业务成功；日志失败不得静默吞掉或改变业务结果。任何跨模块适配都必须保留旧 JSON 字段、功能菜单、业务计算和源文件安全语义。构建、测试、人工验收和 Linux/deb 验证分别记录，写出测试代码不代表测试通过。
