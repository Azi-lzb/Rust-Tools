## 3. Excel COM 深度检查（目标 §15，12 个输出全 PASS）

每个输出在真机 Excel（`DispatchEx`，`DisplayAlerts=False`）中打开 → 检查工作表数量、
数值、日期、百分比、前导零、合并、字体、填充、边框、数字格式、列宽、行高、打印区域、
纸张方向、缩放（FitToPagesWide/Tall）、页脚、导出 PDF、PDF 页数、分页符、
`Cell.Text` 的 `###` 扫描、PDF 文本层的 `###` 扫描。

| 输出 | 页数 | Excel `###` 单元格 | PDF 文本层 `###` | 末行标记 |
| --- | ---: | ---: | ---: | --- |
| 宽表186 mode1（Openpyxl） | 3 | 5578 | 5578 | ✅ |
| 宽表186 mode1（Rust） | 2 | 2819 | 4199 | ✅ |
| 宽表186 mode2（Openpyxl） | 3 | 5578 | 5578 | ✅ |
| **宽表186 mode2（Rust）** | 3 | **0** | **0** | ✅ |
| 宽表210 mode1（Openpyxl / Rust） | 3 / 2 | 6298 / 3179 | 6298 / 4739 | ✅ |
| **宽表210 mode2（Rust）** | 3 | **0** | **0** | ✅ |
| 宽表222 mode1（Openpyxl / Rust） | 3 / 2 | 6658 / 3359 | 6658 / 4979 | ✅ |
| **宽表222 mode2（Rust）** | 3 | **0** | **0** | ✅ |

关键结论：
1. **Rust mode 2 的紧凑自适应彻底消除了 `###`**（Excel 显示层与 PDF 文本层均为 0），
   而 Openpyxl 引擎 mode 2 因缺少自适应仍有 5578 个 `###`。
2. mode 1 两引擎 `###` 数不同（5578 vs 2819），但**不是宽度不同**：按 XML 展开逐列比较，
   186 列宽度**零差异**；Excel COM 直接读两输出的 `ColumnWidth` 也完全一致
   （10.38 / 4.38 / 11.38 / … / 4.38）。差异来自 Excel 对 `<col>` 分组方式的渲染处理
   （openpyxl 每列单条 vs rust_xlsxwriter 合并同宽连续列），属 Excel 显示细节，
   非文件内容差异。
3. mode 1 的 `###` 是**源模板窄列宽的直接结果**（夹具刻意把偶数列设为 5 字符宽），
   mode 1 的语义就是继承源列宽，因此保留 `###` 是正确行为。
4. 打印区域两引擎一致（`$A$1:$GD$62` 等），末行标记 `ROW61END` 在所有输出的 PDF 中出现，
   证明纵向内容未被截断。

### 3.1 横向截断的实测结论（重要）

用 COM 读取末列单元格的 `Left/Width` 与 A4 可打印宽对比（横向 A4 可打印宽 = 741.1 pt）：

| 输出 | 末列右边界 | 可打印宽 | 末列在页内 |
| --- | ---: | ---: | --- |
| 宽表186 mode1（Openpyxl） | 17345.25 pt | 741.1 pt | 否 |
| 宽表186 mode2（Rust） | 17345.25 pt | 741.1 pt | 否 |

合成夹具的 186 列平均列宽 10.1 字符，总宽 1879 字符，是 A4 横向可打印宽（约 105 字符）的
**18 倍**——任何引擎在 FitToPagesWide=1 下都无法把它压进一页（Excel 缩放有 10% 下限，
1879 字符需要约 5%）。这是**物理极限，不是引擎缺陷**，且两引擎行为完全相同。

真实配置里的 186/210/222 列区域确实存在（`打印配置` 第 31–40、63、64、67 行），但真实模板
的列宽由模板自身决定；若真实模板列宽较窄则可放下。**该项需要用户用真实模板确认**，
本轮只能给出合成夹具下的边界结论（见 §7 未测试项）。

## 4. 两引擎的已知行为差异（Openpyxl 入口的既有缺口，Rust 按 print_310.py 语义实现）

### 4.1 mode 2 列宽自适应

- 内嵌 Openpyxl 脚本中 `autofit` / `compact` / `0.95` 出现次数均为 **0**，
  即它没有实现 `print_310.py` 的 `_autofit_block_columns`（min 6.5 / max 18.0、
  `len*0.95+1.2`）与 `_compact_block_row_heights`（15.0）。
- Rust 入口按 `print_310.py` 真实源码实现了这两项。
- 结果：mode 2 下 Rust 列宽自适应（≤18.0），Openpyxl 保留源列宽。
  **这是 Rust 侧的正确行为**（目标 §6/§12 要求 mode 2 紧凑自适应以消除 `###`），
  Openpyxl 入口按目标「不得改变原有 Openpyxl 实现」保持原样。

### 4.2 宽表自动方向

- 内嵌 Openpyxl 的 `parse_orientation` 在 J 列留空时返回 `None` → Excel 落为纵向。
- Rust 按目标 §11「J 列留空时按实际输出区域宽高比判断」实现 → 186 列宽表判为横向。
- 目标 §11「配置指定横向或纵向时，配置优先」两引擎均满足；差异仅在「留空」分支。

## 5. 日期系统与公式缓存验证（目标 §10.3）

| 项目 | Openpyxl | Rust | 结论 |
| --- | --- | --- | --- |
| 1900 日期系统（普通日期/时间/日期时间/自定义格式） | 基准 | 一致 | ✅ |
| 1904 日期系统（同上） | 基准 | 一致 | ✅ |
| 公式缓存日期（`=B2` 缓存值） | 基准 | 一致 | ✅ |
| 公式缓存日期 +1（`=B2+1`，含整天数） | 基准 | 一致 | ✅ |
| 纯时间格式（`hh:mm:ss`，1904 簿） | `13:45:30` | `13:45:30` | ✅ |

1904 簿纯时间单元格的处理是本轮修复项：纯时间串行值是「天的小数」，在两种纪元下显示一致，
不做平移；含整天数的公式缓存（≥1）仍照常平移。修复前 Rust 输出 `1900-01-01 13:45:30`
而 Openpyxl 输出 `13:45:30`，修复后完全一致。

## 7. 真实模板人工验收（2026-11-11 第二轮，用户反馈驱动）

用户用真实模板 `！省信贷收支一批（简表+排名）20260421.xlsx` 人工测试后反馈 4 个问题。
取证材料保留在 `测试用例/3/`（源模板 + 双引擎输出 + `forensic_diff.py`）。
用与用户 config 等效的 `config_check.xlsx`（显式源区域 A1:J42 / A1:HN61 / A1:HB61 ×2、
纵向）重跑双引擎后对拍（重构等效性已验证：新 openpyxl 输出与用户旧输出 0/0/0 一致）：

| 对比 | 值差异 | 样式差异 | 打印设置差异 |
| --- | ---: | ---: | ---: |
| 检查_惠州简表（openpyxl vs Rust） | **0** | 20（全部=主题色，见下） | 0 |
| 检查_三币种（openpyxl vs Rust） | **0** | 3（全部=主题色） | 0 |

反馈问题的处置：
1. **空单元格框线/填充**：已修复（无值但有样式的格输出 blank 保留样式；实测惠州简表
   空样式格 67 个不再缺失）。
2. **没有居中**：已修复（`center` 误映射为跨列居中 `centerContinuous`——3.6 万格；现已分开映射）。
3. **Div0**：已修复（错误值改用 Display 输出 `#DIV/0!`/#REF! 等规范文本）。
4. **数值变文本（绿三角 + 全精度显示）**：已修复（合并区数值锚点保持数值类型，
   C40:D40 等 6 处合并锚点不再文本化；行高 ht=15、列宽 18.625/25.5 的像素级漂移同步修复）。
5. **主题色差异（唯一残余，共 23 格）**：**取证确认这是 openpyxl 引擎的长期失真**——
   源模板主题是 Office 2013 调色板（accent5=4472C4、lt2=E7E6E6），openpyxl 引擎把
   theme 引用复制进「默认 Office 2007 主题」的新工作簿，渲染成 4BACC6/B3B1A9；
   Rust 直接解析源主题 → 4472C4/ADADAD，**与源模板在 Excel 中的真实显示一致**。
   颜色取向已由用户确认（2026-11-11）：**忠实源模板**——Rust 解析源主题的行为
   保持不变，openpyxl 引擎的失真属于其既有行为（按「不得改变原有 Openpyxl 实现」
   原则不动），双引擎主题色差异作为已知差异记录在案。
